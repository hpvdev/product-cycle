# Technical design and service needs

When policy.project_setup_required is true, produce project-setup.json with {stack:{language,runtime,framework,package_manager},structure:["paths and purposes"],coding_rules:["concrete stack conventions"],common_components:["shared components needed before features"],environment_names:["names only"],tooling:{format,lint,typecheck,test},instructions:"concrete setup steps",checks:[["argv for actual foundation checks"]]}. Every tooling field states a tool/command or a reason it is not needed. Structure and coding rules must be nonempty; common components and environment names can be empty. Specify boundaries, dependency policy, errors/logging, configuration and applicable UI conventions.

Project setup follows plan review and is a prerequisite for features and service setup. Choose the lightest sufficient foundation. Graphify is optional for complex existing code relationships; do not install it by default for a new small project.

After product analysis and UX/UI, produce architecture.md covering data, component boundaries, integration choices, risks, recovery and proportionate verification. Identify third-party service needs now, before any real configuration. Do not configure accounts during this design task.

Map design.md's screen/action IDs and shared rules to component boundaries, data/state ownership, validation, persistence and API/error contracts where needed. Separate common technical behavior from screen-specific behavior and reference the functional specification. Do not silently redefine accepted product behavior; resolve contradictions before dependent work.

When policy.service_setup_required is true, also produce services.json: {"services":[{"id":"stable letters/numbers/hyphens","provider":"selected provider","purpose":"requirement and reason","environment":"selected project/environment","inputs":["names of inputs the user must provide, never values"],"permissions":["required scoped rights"],"configuration":"concrete setup steps","verification":"observable proof of readiness","checks":[["argv","for actual connection/permission verification"]],"owner":"who supplies inputs","cost":"expected cost and budget boundary","fallback":"recovery or alternative"}]}. An empty services list is valid if no third-party services are needed. Include Firebase, Resend, AI providers, DNS or other integrations only when required by this product. Distinguish service selection, user-supplied inputs and completed configuration. Never include credential values.

The user supplies missing inputs after design and planning. Setup occurs only after plan review. Name browser/account references and runtime capabilities when relevant; available desktop tabs do not automatically exist in app-server. Determine which increments need each service. Prepare local development and verification. VPS purchase/provisioning and remote release are deferred and must not block local work. Document future server needs without creating accounts or resources now.

For a requested game, read the installed .agents/skills/product-cycle-game-design/SKILL.md and only the companion references for this assigned stage when available. Use its architecture guidance to map accepted gameplay rules to rendering, input/state/time ownership, assets and supported device constraints without choosing a new game concept. If the companion is missing, record the bundle gap and preserve the accepted game intent: player actions, clear rules, world/state consequences and a planned real-play trial must not be reduced to a generic screen list. Do not start dependent work, alter historical evidence or add universal game features merely to satisfy the companion.
