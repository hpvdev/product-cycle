# UX/UI design

Use accepted requirements. Produce design.md with user journeys, screen or interaction structure, empty/loading/error/success states, accessibility needs, and requirement links. Create an appropriate visual work product when the product has a UI: reference images, an editable design export, or a diagram. Do not build HTML/CSS prototypes or run a server to generate design images; interface implementation and checks belong to build/verify. Include its path in the result. A backend-only product may explicitly justify an interface contract instead.

For UI products, design.md is also the readable functional specification: shared business/interaction rules; a screen index and navigation map; and a section per stable screen ID. Each section describes purpose, requirements, entry conditions, displayed data, layout regions and exact visual reference/version/state/viewport. Specify each control/gesture's trigger, availability, validation, processing rule, data/state effects, feedback and destination, with applicable error/recovery behavior and observable acceptance examples. Link shared rules instead of repeating them; visual tokens stay in baseline.rules and implementation/API internals in architecture. Do not leave primary action behavior to the coding worker or treat image generation as a substitute for the spec. Use only applicable states and accepted scope. Reconcile consequential requirement gaps with the owner through the supported workflow before dependent implementation. If the installed design skill is available, read its references/screen-spec.md for the output guidance.

Use connected design tools only if available in this runtime. Record capability gaps. A design description alone does not establish visual or usability acceptance. Keep fidelity proportional to uncertainty; identify what needs a real user or product-owner judgment. Stay within accepted scope.

For an existing UI, use its design system and comparable screens. For a new visual direction, use Product Design and Image Gen when available to explore alternatives, then prepare a specific reference for the product-owner decision. Do not start product implementation or present an image as a working UI. If a required design tool is missing, record the gap rather than inventing tool results. An existing owner-selected reference can be reused without generating alternatives.

Also produce design-baseline.json:
{"has_ui":true,"visual_reference":"project-relative/path/to/reference.png","flows":["Main user journey"],"states":["Empty","Loading","Error","Success"],"rules":{"typography":"...","colors":"...","spacing":"...","responsive":"..."},"acceptance":["Observable visual and interaction checks"]}

Register the actual visual_reference in result.artifacts. A selected Image Gen image can directly serve as the canonical baseline when it clearly communicates layout, hierarchy, colors and components. Set has_ui=false and visual_reference=null only for a product without UI, and describe its interaction contract. Use concrete product content and relevant states. The owner reviews the baseline before downstream work. If the owner requests changes, revise the reference before implementation. Figma is optional; its absence does not block design. Exact image pixel dimensions or aspect ratio are not absolute acceptance conditions; record target screen dimensions, responsive rules and the mapping to the image in design.md.

Use only the current bundled Frontend App Builder concept guidance for UI work; its implementation and browser verification rules apply to build/verify. Cover the full core screen and any materially different sections/states whose details are unclear, rather than generating only a header. Describe every applicable state, reusing the same image when only numbers, text, messages or button states change. Create separate images only for materially different layouts or presentation; do not require a fixed image count. Record reference-to-screen/state coverage in design.md and reusable tokens/components in baseline.rules. Existing accepted references and design systems remain authoritative. Use real product content, code-native controls and assets that can be implemented; missing required Image Gen capabilities must stay explicit.

Each screen.references entry defines one canonical implementation target per screen ID, state and viewport. Multiple targets may share the same image; describe their differences in design.md and cover every declared state without duplicate target keys. Use the selected image directly; no browser capture is required to complete design. Existing supplementary captures can be registered in result.artifacts and linked from design.md.

Images guide appearance; design.md specifies exact labels, symbols, behavior and layout rules. Document minor text, symbol or size discrepancies and intended corrections there. Correct or regenerate an image only when discrepancies obscure the layout or force implementation to guess. Do not require Figma merely because Image Gen cannot reproduce every label or exact pixel dimensions. Build/verify evaluates the accepted image together with these documented rules and corrections.


When policy.collaborative_product is true, collaborate with the owner in Codex on the main journey and visual direction. Show actual alternatives when useful, explain interaction tradeoffs, and iterate the visual reference on their feedback. Carry the approved experience and quality targets into design-baseline.acceptance. Do not equate a beautiful image with usable interaction, or simplify away the accepted differentiating behavior. If required owner discussion is unavailable, record the missing decision as a blocker. The final baseline remains proposed until the owner gate is accepted.

For a requested game, read the installed .agents/skills/product-cycle-game-design/SKILL.md and only the companion references for this assigned stage when available. Use its game-spec guidance alongside the screen specification: define gameplay rules and game feel, an arena/world plus HUD, timing/feedback and registered game art. The concept overview and detailed rules belong in design.md; still images do not prove the loop is playable. If the companion is missing, record the bundle gap and preserve the accepted game intent: player actions, clear rules, world/state consequences and a planned real-play trial must not be reduced to a generic screen list. Do not start dependent work, alter historical evidence or add universal game features merely to satisfy the companion.
