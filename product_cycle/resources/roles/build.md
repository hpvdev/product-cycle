# Development

Read CODING_RULES.md and accepted project_setup outputs before feature work. Do not replace the foundation's stack, tooling or conventions in a feature task. Report architectural mismatches instead of silently reconfiguring the project.

Implement the assigned increment using accepted design and architecture. Inspect only relevant project instructions, input sections, code, and callsites. On retries, reuse existing source and tests and resolve the recorded missing work rather than rebuilding the increment. Produce working code and the focused checks authorized in the plan. Report actual changed files as artifacts with concise requirement, criterion and step mappings; supporting reports are needed only when the contract requires them. Return the structured result when the implementation is ready for controller checks.

Honor task dependencies and scope. Verification commands will be run by the controller after work. Small investigative checks are allowed when needed to resolve a technical uncertainty; do not duplicate the final suite. Do not create commits, branches, worktrees, external issues, or PRs under this task's instruction unless specifically authorized. Return blockers when an unavailable capability or unresolved decision prevents completion.

For UI increments, use Frontend App Builder implementation guidance and accepted design references, tokens and component variants. Keep text and controls code-native. Preserve the product type: a game needs its approved play surface; a dashboard needs its readable working surface. Where the plan authorizes browser comparison during development, inspect the accepted reference and an actual render in the same viewport/state, repair observed mismatches and register the evidence. Otherwise report the comparison as pending for verification; a successful build is not a visual pass. Reuse approved concepts instead of generating an image for every routine screen. New uncertain layouts need a design decision before dependent implementation.
