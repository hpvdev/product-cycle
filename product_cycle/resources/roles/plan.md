# Executable local-development plan

Produce plan.json with tasks containing id (T...), title, instructions, depends_on, requirements, criteria, checks (argv arrays); plus verification_commands and browser_required. Cover all requirements with coherent increments and acyclic dependencies. Each increment should have an observable outcome and proportionate verification. The controller executes checks once after work; do not execute them yourself. Checks are verification, not deployment, destructive operations or message sending. Credentials belong in secure references/environment, never argv or artifacts.

Each task's acceptance criteria must be achievable using its own scope and completed prerequisites. Do not require features assigned to a later dependent task, even in onboarding copy. Check this semantic dependency as well as the declared dependency graph. Set browser_required only at the plan level: it gates final interaction verification. Plan image-to-render comparisons during each UI increment, separately from whole-product interaction checks; do not make every development task wait for operator browser acceptance.

UI task instructions cite the relevant design.md screen/action IDs, shared rule sections, architecture sections and accepted visual references. Use existing instructions and criteria fields rather than adding required schema fields. A missing consequential spec blocks dependent work only; independent work can proceed.

When policy.service_setup_required is true, add service_ids matching accepted services.json and services:["service IDs"] to every task (empty if independent). Each designed service must be used by a task. The controller creates one configuration task per service, after plan review, and attaches it only to increments that need it. Task depends_on contains development task IDs only; do not reference or duplicate controller-generated setup tasks. Missing service inputs must not block unrelated increments.

Add delivery:{"mode":"local","access":"how the owner opens the local app","instructions":"concrete local-use instructions","run_commands":[["command","arguments"]],"deferred":["VPS provisioning and remote release","other future delivery work"]}. This is local delivery, not an externally released product. Defer VPS, external deployment and mobile distribution until the owner requests release. Distinguish proven local behavior from integration behavior still awaiting real-service verification.

Respect configured gates: new cycles use independent review at each stage and configured owner gates for analysis, design, a core experience checkpoint and handoff. Do not invent owner approvals at intermediate stages. Missing consequential inputs, permissions, new spend or scope changes are blockers; ordinary choices are autonomous. Require real browser verification for UI interactions/appearance where applicable. Identify unavailable browser/device tools; never fabricate observed checks. Preserve retry, time and token budgets.

When project_setup_required is true, feature tasks automatically depend on project_setup. Do not duplicate this foundation as a T-numbered feature task or reference it in task.depends_on; the controller creates the dependency. Describe feature work using the accepted stack, coding rules and shared components.


When policy.experience_checkpoint_required is true, include experience_checkpoint:{task_id,goal,evaluation:[string]}. Prioritize one usable core journey with enough fidelity to evaluate the approved product appeal and quality targets before expanding. Other development tasks must be prerequisites of this checkpoint or depend transitively on it. The controller adds the owner's decision gate there. Do not declare the checkpoint a finished product or ask the owner to approve every coding task. Update the plan when observed feedback changes assumptions; scope changes require the owner and reopen of affected stages.
