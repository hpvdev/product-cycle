# Product-specific verification

Architecture produces verification.json with version:1, surface (web/desktop/mobile/game/cli/api/library), environment:{runtime,requirements:[string],instance_policy:"exclusive"|"isolated"}, launch:{commands:[[argv]],instructions,ready}, doctor:{commands:[[argv]],instructions,read_only:true}, cleanup:{commands:[[argv]],instructions,preserve_evidence:true}, and procedures:[{id,actions:[string],expected:[string],evidence:[string],commands:[[argv]]}]. Commands use argument arrays; never place credentials in them. Empty command lists are valid for genuine native/manual actions, with concrete instructions and required capability identified. Do not run a server or prototype during design merely to create images.

Describe the actual user-facing path, readiness checks, test data, authorized account references, device/browser/runtime requirements, isolation and cleanup. Reuse existing project tooling. Planned procedures are not completed verification. Build confirms the available commands and implementation entry points.

Build, integration and whole-product verification produce runtime-observations.json with version:1, source_fingerprint, environment:{runtime,instance,surface}, and features:[{id,status:"pass"|"fail"|"blocked",observations:[{procedure,action,expected,actual,evidence:[project-relative paths]}]}]. Each observation names an assigned verification procedure; PASS covers every procedure assigned to that feature. Register each referenced artifact. Capture the action and its resulting state, including relevant side effects, not just a screenshot of the final screen. Never use the report itself as proof. PASS requires actual evidence and independent review; FAIL requires repair; BLOCKED retains the missing input/capability and clearing action. Preserve all evidence during cleanup.

Integration also produces feature-map-update.json with version:1 and features:[{id,implementation_status:"observed",code_entry_points:[actual project-relative files]}] for its assigned features. Whole-product verification exercises the main journey, cross-feature interactions, applicable UX/visual consistency, performance and error recovery on the exact canonical source version intended for handoff. Use the accepted design image together with documented label, symbol and responsive corrections.

For whole-product verify, add whole_product with keys main_journey, cross_feature, ux_consistency, visual_consistency, performance and error_recovery. Each has status:pass|fail|blocked|not_applicable, a concrete reason and evidence:[registered paths]. The main journey is always applicable; justify any other omission against accepted scope. A completed verify result has only pass or justified not_applicable outcomes. Review assesses those observations and omissions semantically; JSON validation alone never proves the product works.
