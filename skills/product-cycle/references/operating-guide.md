# Operating the packaged controller

Run commands from the Product-Cycle repository, or use `product-cycle` after local installation. Replace example paths with the user's selected project.

1. Create a brief with desired outcome, users, scope, constraints, and known unknowns.
2. `python3 -m product_cycle init --project /absolute/project --brief /absolute/brief.md --name "Product name"`
3. `python3 -m product_cycle serve --project /absolute/project`
4. `python3 -m product_cycle run --project /absolute/project`

For an explicitly selected autonomous team, add `--team` to `init` and use `supervise` instead of the native `run` loop. Read [team operation](team-operation.md) for the separate background service, role sessions, peer exchanges, owner gates and recovery. The office view observes activity; opening the dashboard does not start workers. Existing projects require an explicit idle migration rather than an automatic upgrade to team mode.

`run` with codex-app-server advances ready tasks sequentially, with a separate read-only review session. With the default codex-desktop executor it prepares a native handoff; the active Codex session executes it using the loop below. It stops at a product-owner decision, a blocker, an explicitly configured budget limit, or no ready work. New local cycles track token usage without a token ceiling; `init --max-turn-tokens N` and `--max-cycle-tokens N` opt into positive limits. In an idle cycle's config.json, `null` disables the corresponding ceiling; existing numeric limits are preserved. Timeouts and retry limits still apply. New local cycles have owner gates at analysis, design, the plan-defined core experience, and handoff, with independent review at each stage; existing cycles keep their configured gates. Respect authorization already supplied when recording decisions; never invent it.

`decide --project ... --task handoff --action approve --actor "Owner" --note "Accepted verified local product"` records a decision tied to the reviewed revision. `reject` returns it for rework. `reopen --task ... --note ...` starts a revision and invalidates dependents without deleting evidence.

`pause` takes effect at task boundaries. `resume` lifts that pause; use `run` to continue. After a controller crash, `recover` marks unfinished work blocked. Inspect actual changes, then use `reopen` before repeating work. Third-party setup starts after design and plan review, scoped to the selected accounts/project. Missing inputs block dependent increments; independent work can continue. VPS provisioning and external deployment/publication are deferred.

For a human-requested restart from the beginning or a major stage, use [product-cycle-reset](../../product-cycle-reset/SKILL.md). Reopening invalidates results but cannot clear chat messages. Execute restarted work in a new empty chat/session using the minimal restart handoff and current request, rather than continuing or forking the old conversation. Preserve historical artifacts for audit; do not load them as current product inputs. A partial restart retains accepted upstream inputs.

Codex must be installed and authenticated. `doctor` reports availability without secrets. Browser/MCP capabilities from desktop are not assumed to exist in app-server. If browser acceptance is needed and unavailable, the operator records real observations with `browser-evidence`, then invokes `review`. `judge` sends explicitly supplied non-sensitive text to Jev for a semantic opinion.

`package --output /outside/project/delivery` exports source, evidence, decisions, and full history after all stages are accepted. It skips .env files and symlinks, listing omissions in the manifest. It does not deploy; handoff.md explains setup and product version.

`init` prepares Git, .gitignore, AGENTS.md, PRODUCT_CYCLE_RULES.md and the bundled skills without replacing existing user instructions or publishing. Inside Development, architecture and plan precede the preparatory project_setup task, which creates CODING_RULES.md, source/tooling foundations and local checks before features. Use `doctor --project ...` for project readiness and `bootstrap --project ...` to adopt missing or explicitly reviewed common-rule changes in an idle old cycle. The pip-installed CLI also offers `install-skills`.


## Native Codex loop

Read status, the selected project's instructions and its executor. Do not assume that preparing a request starts an AI worker. A running Codex session must own this loop; without it the dashboard honestly shows waiting. Prefer the current project chat for interactive analysis/design. Continue existing task chats only with the human's authorization. Create a user-owned chat only when the human explicitly requests it. If an independent reviewer session is needed, delegate a read-only review using the available subagent capability; bind that session's actual Codex thread if the host exposes one. If the host does not expose a usable independent session, report that capability gap rather than reviewing your own work or inventing a session.

1. `product-cycle run --project /absolute/project` returns a request with exact task/attempt, prompt and result paths, short title, requested model/effort, and work/review phase. Read the request and prompt. Repeated requests reuse the same pending handoff.
2. Bind before work using `product-cycle desktop-bind --project ... --task ... --attempt ... --thread ...`. Supply the actual project chat identity obtained from the host, not an invented value. A reviewer must be independent of worker chats. A bound chat's configured model is a request, not proof of the actual model; use native host model selection when supported, otherwise disclose that limitation.
3. Execute in Codex with visible commentary. For analysis, interview the owner and record supplied answers through `owner-input --project ... --task analysis --actor ... --note ...`. For design, discuss real references/prototypes and record the feedback similarly. Do not make the owner manipulate CLI commands. Only store safe summaries, never credentials. The prompt contains the exact output schema.
4. Write the result to the supplied result path. For progress use `desktop-progress --project ... --task ... --attempt ... --file /project/progress.json` with the existing update_plan entries; progress is advisory. Submit using `desktop-submit --project ... --task ... --attempt ... --file /assigned/result.json`. This runs planned checks, preserves browser gates and queues a separate review. A worker must not approve its own work.
5. The orchestrating session reads status and repeats run for the independent review, then for the next ready work. Do not ask for confirmation at every task. At an owner gate, show the concrete output in Codex, discuss revisions, and record the owner's actual decision using decide. After approval, repeat run. Reject repairs that stage; changing approved scope uses reopen and invalidates dependents. Pause/resume also happens in Codex.

The dashboard polls state every three seconds and reads completed chat results every fifteen seconds while it runs. Native workers can return a friendly final message after saving result.json; the controller reads that assigned file only after observing a completed turn, and still validates all contracts. desktop-submit can explicitly submit from the bound session without waiting for chat completion. Neither path turns prose into approval.

Token totals use native session usage counters when present. Binding records a baseline and repeated polling updates the delta, without adding the same thread total twice. Missing counters/baselines remain unknown. Counters describe model tokens, not billing; model choice and effort remain separate from measured usage. Optional budgets are checked at native dispatch boundaries; this adapter does not interrupt Desktop turns mid-generation. The counters are a compatibility reader for local Codex session logs, not a promise that every host/version exports usage.

## Existing cycles

`configure --project ... --executor codex-desktop` switches an idle cycle to native execution and a read-only dashboard without rewriting evidence, accepted scope, or gates. Existing cycles without an executor retain App Server behavior until explicitly migrated. Do not retroactively mark old decisions approved. To adopt the collaborative product contract on an existing product, first discuss re-scoping with its owner, reopen analysis, and explicitly enable collaborative_product, experience_checkpoint_required and the analysis/design/handoff gates in its configuration. Reinstalling skills or rules needs explicit review and bootstrap; do not overwrite a running product's recorded foundation.
