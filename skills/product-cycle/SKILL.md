# Product Cycle

Use this skill when the user wants the packaged workflow applied to a selected product. Preserve the selected product, repository instructions, and authorized scope. For a narrow code task, use only the relevant task contract rather than restarting the full cycle.

The controller is the source of truth for task state. Use its status output to find the current task, accepted inputs, evidence, and decisions. Read [the operating guide](references/operating-guide.md) when initializing, resuming, recording decisions, or packaging a cycle. Read [contracts](references/contracts.md) when producing or reviewing a stage output.

The bundle includes product-cycle-project-setup, product-cycle-setup, product-cycle-analysis, product-cycle-design, product-cycle-architecture, product-cycle-plan, product-cycle-build, product-cycle-verify, product-cycle-handoff, product-cycle-retro, and product-cycle-review. For a requested game, also read [product-cycle-game-design](../product-cycle-game-design/SKILL.md) as a domain companion within the assigned stage. It supplies concept patterns, gameplay specifications and stage-appropriate review; it does not start an extra stage. Load only the skill for the assigned stage; review uses its own skill. For a human-requested reset from analysis or a major stage, use [product-cycle-reset](../product-cycle-reset/SKILL.md); it is an orchestration operation, not another product stage. Do not start parallel agents merely because the skills are separate.

If you are already a worker inside a controller-supplied context packet, complete that assigned contract and return its result. Do not invoke the controller recursively. Use work_steps to report advisory progress; every completed step must link concrete outputs. The controller and independent review establish confirmed status.

Work toward the assigned outcome using relevant accepted inputs. Keep facts, assumptions, open questions, and observations distinct. Supply actual files and criterion/requirement mappings. Record a blocker when a consequential decision or required capability is missing.

Submit work for independent review. Completion requires the stage contract, recorded checks where applicable, adequate evidence, and any defined product-owner decision. Do not infer a passed check from a proposed command or a screenshot from a description.

The controller owns state, immutable evidence, dependency changes, and delivery packaging. Do not edit its database or evidence objects. Scope changes go through reopen, preserving history and invalidating dependents. Retry budgets do not imply completion. Retro proposals are evaluated before adoption.

For a human-requested skill update in an existing project, preview with `update-skills --project ...` and inspect the changed files; select relevant skills with repeated `--skill` flags. Apply the authorized scope with `--apply` only after its writers stop. Known unchanged originals can be updated automatically; conflicts need reconciliation or the human's explicit choice to replace selected customizations using `--replace-customized`, which keeps backups. Do not treat approval to update as approval to discard custom guidance. Re-read the updated skills in the active chat. The command records the new foundation but does not replay completed stages or change policy; use the reset skill only when rerunning is requested.

For a human-requested uninstall/reinstall, preview `uninstall-skills --project ...`, then use `--apply` after writers stop. Customized/unknown copies require an explicitly authorized `--force`; the old folders and manifest are backed up. `install-skills --project ...` then installs the bundle from the selected Product-Cycle checkout/package and records the new foundation. Keep source, state, common rules and unrelated skills. Uninstall/reinstall does not reset a cycle or clear a chat; use a new chat for the new instructions. Updating the controller from Git/package installation is separate from `update-skills`; stop the old server and use the updated executable before syncing project skills. Do not install the bundle into the Product-Cycle development repo merely because you are editing it.

Read project AGENTS.md, PRODUCT_CYCLE_RULES.md and CODING_RULES.md when present. New cycles prepare Git, common rules and skills during init, then require the preparatory project_setup task inside Development after architecture and plan.


New cycles execute in Codex Desktop by default. The dashboard reads status and evidence; it does not drive execution or record owner decisions. In a native session, use the operating guide's native handoff loop. Never launch a separate writer for a Desktop-owned chat. App Server remains an explicitly selectable executor for unattended sessions. When the owner explicitly selects autonomous team mode, read [team operation](references/team-operation.md): the background supervisor owns dispatch and role sessions, while the office dashboard observes their recorded activity. Do not start a second orchestrator from a team worker.

Follow the selected policy, not the presence of a team or an office illustration. With team.enabled and team.policy = autonomous, collaborate with the owner during analysis and preserve its required human gate. After accepted analysis, Design Director and Art Director choose the design baseline under delegated company authority; build, verification and independent review continue within accepted scope. Human final acceptance is optional under this policy. Record company decisions as company decisions, never as human feedback or approval. In supervised mode, retain configured owner gates for direction, design, the first usable core experience and delivery. Existing projects keep their policy until explicitly changed. In either mode, ask consequential questions with a reason, meaningful options and a recommendation; do not silently simplify the approved experience.

When the owner authorizes the current native Desktop chat to fulfill queued image or browser requests, read [company capability worker](../product-cycle-company-worker/SKILL.md). An App Server worker requests missing capabilities through its actual peer tools; it does not impersonate that native chat or start another supervisor. For an assigned company improvement mission, read [bounded guidance improvement](../product-cycle-improve/SKILL.md); ordinary product workers and retro proposals do not modify installed skills themselves.
