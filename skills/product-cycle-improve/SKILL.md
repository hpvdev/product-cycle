# Improve workflow guidance

Use genuine failed or inefficient missions to propose a small guidance experiment. Preserve product scope and current evidence; an improvement candidate does not authorize changes to controller rules or completion criteria.

Write `candidate.json` using [the experiment contract](references/experiment.md). Only controller-listed `references/learned-guidance.md` targets are eligible. Preserve the current before hash. State one observable hypothesis, relevant raw cases and genuine evidence paths. Do not edit installed skills or submit executable commands.

The controller runs its registered checks. In a separate evaluation mission, forward-test the same raw cases against the sealed before and after guidance, recording actual outputs, benefit and regressions. Passing structural checks alone does not establish improved decisions. Keep synthetic evaluations and real provider/product evidence clearly identified.

A fresh independent reviewer inspects the exact candidate, case outputs and check logs. Reviewer, evaluator and author use different identities and threads. Reject unsupported benefit, expanded permissions, changed goals or weaker acceptance. Application belongs to the controller at a stable point; it preserves originals, records version hashes and follows installer customization protection. Subsequent monitoring can trigger rollback, with the same stable-point and customization checks.

If evidence, capabilities or a stable application point are missing, keep the candidate pending or rejected with its actual reason. Do not turn an unsuccessful experiment into a successful version by editing its evidence.
