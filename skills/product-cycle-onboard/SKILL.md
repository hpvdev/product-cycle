# Open the company, then receive the request

The owner should see the office first, give the company a goal in this Codex chat, then observe actual employees and conversations as they start work. The dashboard observes; it is not a replacement chat or a wizard that the owner must operate at every stage. Read project instructions and common rules. Reuse the installed Product-Cycle executable or the selected workflow checkout; do not install the bundle into its own development repository.

For a new project, require only a selected folder and office name to open the company. Derive the name from the folder when sensible; ask only if the project is unclear. Do not ask for a complete PRD, screens, stack, provider accounts or budget before opening the office. Do not invent a product request to initialize it.

1. Run `product-cycle onboard --project /absolute/project --name "Office name" --open`. This prepares Git, rules and skills, creates a paused company awaiting a real request, and starts only its local dashboard on an available port. No product worker starts. For an existing cycle, omit the name; preserve its tasks, history, runtime and policy. The command does not overwrite an existing brief.
2. When the host exposes the actual current owner chat identity and it belongs to the selected project, bind it using `onboard --project ... --owner-thread ACTUAL_ID`. The controller checks metadata without reading turns and rejects worker-session identities or another project. Never guess a chat ID; if the host cannot supply it, retain this chat as the owner interaction surface and state that a direct owner-chat link is unavailable.

   Read the returned `dashboard_url` and connection status. Open that exact verified URL in the available host browser/panel, or give the clickable link if UI opening is unavailable. Never assume 8787 is the selected project's port or show an unrelated office. Explain: “The company is open. Its employees are waiting for your request; no AI task is running yet.” Do not start the supervisor just to animate the office.
3. Invite the owner to describe what they want to build in this chat. If they already described it, use those exact facts after opening the office; do not ask again. Save their initial request as a brief file, without filling unknowns with invented decisions. Show a short summary for correction, including the selected project and how the company will collaborate. For this autonomous company, the owner works with the analysis team and approves analysis before dependent design/development. Later routine decisions are delegated within that accepted scope; consequential missing goals/access/cost still require owner participation. Brief submission is not analysis approval.
4. For a new office awaiting a request, run `product-cycle onboard --project ... --brief /absolute/request.md --start`. It records the actual request and starts one supervisor. Read `onboard --project ...` again after startup and report observed status. Process launch alone is not confirmation of an active worker: wait for actual supervisor/session records, using short interruptible observations. If startup fails, show the specific missing preparation/access and preserve the office; do not claim the company is working. A deliberately paused existing project is not automatically resumed by onboarding.
5. Keep the owner in this chat during analysis. The notification opens the bound owner chat; the source worker chat is for inspection, not the response channel. When the owner answers here, identify the corresponding current open question and record the actual response with `team-answer --project ... --question ACTUAL_QUESTION_ID --actor "Chủ sản phẩm" --answer "Exact owner answer"`. If several questions could match, clarify the target rather than answering all of them or guessing. Read actual project state and pending `team-answer` questions, ask the owner the consequential question and record their actual answer; never fabricate one. Register analysis approval only when the owner really accepts its current outputs. Independent work proceeds according to the controller. Avoid launching a second supervisor or independently editing the product beside its worker.

Questions awaiting the owner must stay visible with a message badge on the sender and a prominent action notice, including the exact question, verified owner-chat reply link when available, and optional source-session link. Clear them only after a recorded answer, and keep stale questions as history rather than current actions.

The office must display a clear company state, readable employee names independent of zoom, current tasks, last observed activity and real recorded session links. Keep the employee list open on the left and project conversations open on the right by default; recorded questions, replies and conclusions update continuously without opening individual messages. Return the project dashboard link and existing chat links from `onboard` output. If no session is recorded, say that it has not been created. App Server sessions may not be listed in Codex Desktop; do not promise visibility without confirmation. The office's activity/detail view remains available, and the native chat stays here. Never invent a thread identity or create/send to user-owned chats without their explicit authorization.

Verify configuration rather than asking the owner to choose every technical value: role models/effort, selected policy, local delivery and runtime. The file is the configuration source. The dashboard summarizes it read-only. Identify third-party services after analysis/design; do not request irrelevant accounts at startup. External deployment and VPS remain deferred in the current workflow.

For native image/browser requests, use the existing [company worker](../product-cycle-company-worker/SKILL.md) in the owner-authorized current chat. Verify real tools and chat identity before binding a job. A queued job or an employee title does not prove capability. If the current runtime cannot expose the required tools or identity, state that gap; do not promise background native execution when this chat is inactive.

The dashboard receives recorded information over its live connection and reconnects with a fresh snapshot. Losing that connection means the displayed data may be stale, not that the product is necessarily stopped. Distinguish dashboard connectivity, supervisor connectivity, actual worker activity, a legitimate question wait and an unresolved execution outcome. Do not fabricate dialogue or progress, and never restart unknown operations blindly.
